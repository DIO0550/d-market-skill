# Skill Evaluator

作成済みAgent Skillの品質を測り、回し、改善するためのガイド。
Anthropic公式ドキュメントの評価・イテレーションのベストプラクティスに基づく。

評価〜改善の全体フロー：

- スキルを実行せずファイルだけを読む静的レビュー（無駄な記述・フロントマター）で、安く直せる問題を先に潰す
- テストプロンプト（eval）を作成し、スキル付きClaudeで実行する
- ユーザーと一緒に結果を定性的・定量的に評価する
  - ラン実行中にアサーションを作成し、ユーザーに結果を見せる
- 不明瞭点・裁量補完を起点にスキルを改善する
- 収束基準を満たすまで1テーマずつ繰り返す
- hold-out で過適合を検出し、必要なら description のトリガー精度を最適化する

ユーザーがこのプロセスのどこにいるかを判断し、適切な地点から支援する。「無駄な記述がないか見てほしい」「フロントマターを見直したい」なら Phase 0 だけで完結してよい、「ベンチマークだけ測りたい」なら Phase A〜B のみ、「改善まで回したい」なら改善ループへ。スキルの新規作成・構造設計・本文執筆そのものが必要なら `skill-authoring-guide` に案内する。

---

## ユーザーとのコミュニケーション

評価対象のスキルパスと、目的（一度だけ測る／回帰チェック／改善ループ）を最初に確認する。技術リテラシーのコンテキスト手がかりに注意する：

- 「evaluation」「benchmark」はボーダーラインだが概ねOK
- 「JSON」「assertion」はユーザーが知っていることを確認してから使う

疑わしい場合は簡単に用語を定義してから使う。

## Phase 0: 静的レビュー（無駄な記述・フロントマター）

スキルを**実行せずに**ファイルだけを読んで問題を洗い出す。ランを回さないので数分・低コストで終わる。ここで直せるものを先に直してから eval に進むと、イテレーション回数が減る。

判定基準の詳細は [references/static-review.md](references/static-review.md)。結果は `<workspace>/static_review.json` に保存（スキーマは [references/schemas.md](references/schemas.md) 参照）。

**Step 0-1: 配布先を確認する**

「このスキルを Claude Code の中だけで使うか、claude.ai / Skills API にも出すか」をユーザーに聞く。**フロントマターの合否がこれで変わる** — Claude Code 内なら全フィールドが使えるが、claude.ai へのアップロード・Skills API・`package_skill.py` では spec の6フィールド（`name` `description` `license` `compatibility` `metadata` `allowed-tools`）以外があるとパッケージングがハードエラーになる。不明な場合は Claude Code 内のみを既定とし、採用した前提を結果に明記する。

**Step 0-2: 無駄な記述を検出する**

起点は「**この記述を削ったら、スキルなしのClaudeと違う結果になるか？**」。ならなければ削除候補。あわせて、`description` が約束している範囲に対して本文の指示量が見合っているかを見る — 指示は多いほど良いのではなく、強調と分岐が増えるほど1件あたりの効力は下がる。

検出パターン（詳細と対処は static-review.md）：ベースライン知識の再記述 / 目的外の指示 / 重複 / 無根拠の強調（ALWAYS・NEVER・必ずの連発）/ 過剰な例示 / 自明な手順の分解 / 発火しない条件分岐 / 前置き・メタ説明 / references に移すべき詳細 / 参照されないリソース。

**削減提案には必ず根拠（`evidence`）を付ける。「短くできる」は根拠ではない。** そして削ってはいけないものを先に除外する — eval で `ambiguity_point` として報告され、それを埋めるために追加された記述、失敗事例に基づく制約、境界値やフォーマットを指定する1行、reference/script を読むタイミングの指示。`iteration_log.json` があるなら読んでから判断する（過去のイテレーションが足した記述を無自覚に削り戻さないため）。

**Step 0-3: フロントマターを検査する**

現行の全フィールドと配布先ごとの制約は [references/static-review.md](references/static-review.md) の表を参照する（フィールドは追加・変更されるので、記憶ではなく表を読むこと）。**違反**（未知のフィールド、配布先で禁止されたフィールド、`metadata` がマップでない、`description` + `when_to_use` が 1,536 文字超、プラグインスキルでの `name` とディレクトリ名の不一致）と、**改善提案**（`description` に「いつ使うか」が無い、副作用のあるスキルに `disable-model-invocation` が無い、`allowed-tools` / `disallowed-tools` / `context: fork` / `paths` / `user-invocable` の活用余地）を分けて出す。

改善提案は「なぜそのフィールドが要るか」を1文で書けないものは出さない。現状のままが妥当なケースも多い。

**Step 0-4: 結果を報告し、進路を決める**

`summary.verdict` で切り分ける：

- `blocking`（critical あり） — 先に直す。ロードもトリガーもされない状態で eval を回しても意味がない
- `needs_changes` — eval には進んでよい。findings は Phase B 以降のイテレーションテーマの候補として持ち越す
- `clean` — そのまま Phase A へ

**削減案は静的レビューだけで確定させない。** ここで出るのは仮説であり、確定させるのは実測 — 削減案を適用した版で Phase B を回し、**パス率が下がらないまま** トークン数・ステップ数が減ることを確認する。パス率が下がったなら、その記述は無駄ではなかったので差し戻す。

## Phase A: eval テストケースの作成

評価対象スキルに対し、以下の構成でテストケースを作成。ユーザーに確認してから実行。テストケースは `evals/evals.json` に保存（スキーマは [references/schemas.md](references/schemas.md) 参照）。

**シナリオ構成（最低3つ）：**
- **median** 1個 — 典型的な使用ケース。このスキルが最も頻繁に受けるタスク
- **edge** 1-2個 — 境界条件、異常入力、エラーが起きやすい状況
- **hold-out** 1個（推奨） — チューニング中は実行しない。イテレーション3以降、または収束判定時に初めて投入し、過適合を検出する

初期は3件で十分（改善初期は変更のインパクトが大きく少数でも検出できる）。スキルが成熟したら、実運用での失敗事例や「リリース前に毎回手動確認している挙動」からテストケースを採取して20件以上に拡大する — 実分布を反映しないevalは改善しても実利用の品質につながらない。

**expectations の設計：**
- 各期待値に `critical` フラグを設定。criticalは**全パス必須** — 1つでもフェイルすれば改善が必要
- 良いアサーションは**識別的**: スキルが正しく動けばパスし、失敗すればフェイルする。どちらでもパスするアサーションは無価値
- **経路ではなく成果物を検証する** — 「特定のツールを特定の順序で使ったか」のような手順チェックは脆い（エージェントは別の有効な経路で同じ目標に到達しうる）。最終成果物・環境の終状態を検証する
- **主張ではなく実状態を検証する** — エージェントが「完了した」と言ったかではなく、生成ファイルや環境に実際に結果が存在するかを検証する。graderがチートできないアサーションにする

**reference solution（推奨）：**
各テストケースについて、全expectationsをパスする正解出力を1つ用意する（`evals/reference/` に配置）。タスクが解決可能であることと、アサーションが正しく構成されていることの両方を事前に証明できる。

```json
{
  "skill_name": "example-skill",
  "evals": [
    {"id": 1, "prompt": "典型タスク", "category": "median", "holdout": false,
     "expectations": [{"text": "必須要件", "critical": true}]},
    {"id": 2, "prompt": "エッジケース", "category": "edge", "holdout": false,
     "expectations": [{"text": "エラーハンドリング", "critical": true}]},
    {"id": 3, "prompt": "hold-outタスク", "category": "median", "holdout": true,
     "expectations": [{"text": "基本要件", "critical": true}]}
  ]
}
```

## Phase B: テスト実行・採点・ベンチマーク（一連の流れで止めない）

結果は `<skill-name>-workspace/` にスキルディレクトリの兄弟として配置。iteration-N/eval-N/ で整理。

**Step 1: 全ランを同時に起動（スキルあり＋ベースライン）**

各テストケース（`holdout: true` を除く）に対して、同じターンでサブエージェントを起動:
- **スキルありラン**: スキルパス、タスク、入力ファイル、出力先を指定
- **ベースラインラン**: 新規スキルなら「スキルなし」、改善ならスナップショットした旧版
- **信頼性モード**: ベンチマーク/収束判定時は各構成3並列。クイックイテレーション中は1回でOK
- **信頼性指標の使い分け**: 「たまに成功すればよい」タスクはpass@k（k回中1回成功）、ユーザーが毎回頼るスキルはpass^k（全k回成功）で測る。単発成功率75%でも3回連続成功の確率は約42% — 平均パス率だけでは「たまに成功する」と「常に成功する」を区別できない
- **モデル横断テスト**: スキルを複数モデルで使う予定なら、利用予定の各モデルでランを実行する。小さいモデルには情報不足、大きいモデルには過剰説明という形で最適な詳細度が異なる

**実行レポートの要件**: サブエージェントへのプロンプトに以下を含める — 「タスク完了後、`outputs/execution_report.json` を作成する。スキルの指示で**不明瞭だった箇所**（ambiguity_points）と、指示に記載がなく**独自判断した箇所**（discretionary_fills）を記録する」。このレポートがイテレーション改善の最も重要なシグナルとなる。スキーマは [references/schemas.md](references/schemas.md) 参照。

**重要**: 再評価には必ず新規サブエージェントを使用する。同じインスタンスの再利用は前回のコンテキストを保持するため偽の改善を生む。

各テストケースに `eval_metadata.json` を作成（記述的な名前を付ける）。

**Step 2: ラン実行中にアサーションを作成**

待機中に定量的アサーションをドラフトし、ユーザーに説明する。良いアサーションは客観的に検証可能で記述的な名前を持つ。主観的スキルには無理にアサーションを当てはめない。

**Step 3: ラン完了時にタイミングデータをキャプチャ**

サブエージェント完了通知から `total_tokens` と `duration_ms` を即座に `timing.json` に保存。これが唯一のキャプチャ機会。

**Step 4: 採点・集計・分析**

採点方法は「コード → LLM → 人間」の優先順で選ぶ。ファイル存在・フィールド値・diffのように機械的に検証できる期待値はコマンド実行やスクリプトで採点する（速く、安く、再現可能）。ニュアンスの判断が必要な期待値のみLLM graderに回し、人間のレビューはgraderの判定が信頼できるかの確認（較正）に使う。

1. **採点**: [agents/grader.md](agents/grader.md) を読んで各アサーションを評価。`grading.json` に保存。`text`, `passed`, `evidence` フィールド必須。graderは `execution_report.json` も読み、不明瞭点・裁量補完をgrading結果に含める。graderには**必ず新規サブエージェント**を使い、実行エージェントのコンテキストを引き継がせない — 自分の実行を自分で採点すると甘い判定に偏る（self-preference bias）
2. **集計**: ベンチマークデータを `benchmark.json` に集計（スキーマは [references/schemas.md](references/schemas.md) 参照）。収束判定データも含める
3. **分析**: [agents/analyzer.md](agents/analyzer.md) を参照してベンチマークデータのパターンを分析。不明瞭点のトレンドと収束状態を評価

**Step 5: フィードバックを読む**

ユーザーが完了したら `feedback.json` を読む。空のフィードバック = 問題なし。具体的な不満があるテストケースに改善を集中する。

> 「ベンチマークを測るだけ」が目的ならここで完了。結果（パス率・トークン・実行時間・不明瞭点）をユーザーに報告する。改善まで進む場合は次へ。

## スキルの改善

### 改善の考え方

1. **フィードバックから汎化する** — スキルは数百万回使われる可能性がある。少数の例への過剰適合やMUSTの連発ではなく、異なるメタファーやパターンを試す
2. **プロンプトをリーンに保つ** — 役に立っていない部分は削除する。トランスクリプトを読み、スキルが非生産的な作業をさせていないか確認。削除候補の洗い出しには Phase 0 の検出パターン（[references/static-review.md](references/static-review.md)）を使う。イテレーションは記述を足す方向に偏るので、削る側のテーマも定期的に選ぶ
3. **WHYを説明する** — 大文字のALWAYS/NEVERや超厳格な構造はイエローフラグ。理由を説明してモデルの理解を促すほうが効果的
4. **テストケース間の繰り返し作業を見つける** — 全テストケースで独自に似たスクリプトを書いている場合、それをスキルにバンドルすべきサイン
5. **不明瞭点と裁量補完が改善の最大シグナル** — パス率やメトリクスより、execution_reportの `ambiguity_points` と `discretionary_fills` を優先する。実行時間の短縮は本文削減で簡単にできるが、曖昧さの解消がスキル品質の本質

### eval自体を疑う（meta-evaluation）

スコアが伸びないとき、原因はスキルではなくeval側にあることが多い。トランスクリプトと採点結果を実際に読み、「失敗が公正に見えるか（何をどう間違えたか明確か）」を確認する：

- **硬直的な採点**: 有効なバリエーション（別の正しいフォーマット、別の有効な手順）をフェイルにしていないか
- **曖昧なタスク仕様**: 良いタスクの基準は「2人の専門家が独立に採点して同じ合否判定に達する」こと。満たさないevalはメトリクスのノイズになる
- **検証不能なアサーション**: 利用可能な出力からは実際に確認できない期待値がないか

graderの `eval_feedback` が改善提案を含む場合は、スキルの修正より先にevalを修正する。eval修正後のパス率は修正前と比較できないことに注意。

### 1イテレーション1テーマの原則

各イテレーションでは**1つのテーマのみ**を修正する。最もインパクトの大きい不明瞭点（または裁量補完）を1つ選び、最小限の変更で対処する。

理由：複数の変更を同時に行うと、パス率が上がっても下がっても原因を特定できない。1つずつ変えれば、各変更の効果を正確に測定できる。

例外：2つの問題が同じセクションにあり、同じ編集で解決できる場合は組み合わせてOK。

各イテレーションの記録を `iteration_log.json` に保存する（スキーマは [references/schemas.md](references/schemas.md) 参照）。

### tool_usesによる構造的健全性チェック

パス率100%でも `total_tool_calls` が15以上なら、スキルの自己完結性が低い。AIが参照ファイルの読み込みや探索的な操作を過剰に行っている。対策：
- 頻繁に参照される情報をSKILL.md本文にインライン化
- 参照ファイルの読みタイミングを明記（「Step 2でreferences/forms.mdを読む」）

### イテレーションループ

1. execution_reportの不明瞭点から最もインパクトの大きい1件を選ぶ（Phase 0 の `static_review.json` に未対応の finding が残っていれば、それも候補に含める）
2. スキルに最小修正を適用（1テーマ）
3. 全テストケース（holdout除く）を新しい `iteration-<N+1>/` に再実行（Phase B）
4. 採点・分析し、`iteration_log.json` に記録
5. ユーザーのレビューを待つ
6. フィードバックを読み、次のテーマを選択

### 収束・発散・打ち切り基準

**収束（チューニング完了）:**
連続2回のイテレーションで以下を全て満たす → 完了
- 新規不明瞭点が0
- パス率向上 ≤ 3ポイント
- ステップ数 ±10%以内
- 実行時間 ±15%以内

収束したと判断したら、**Phase 0 を再実行する**。イテレーションは記述を足す方向に偏るため、この時点のスキルには初回には無かった重複・過剰な強調・目的外の指示が溜まっていることが多い。ここで削り、削減後にもう一度 Phase B を回してパス率が下がらないことを確認してから完了とする。

**発散（構造的書き直しが必要）:**
3回以上のイテレーションで不明瞭点の数が減少しない → パッチを重ねても改善しない。問題のあるセクションを別の角度から書き直す。

**打ち切りの目安:**
- 50→80%: 効率帯。1-2イテレーションで大幅改善が見込める
- 80→90%: 2-3イテレーション要
- 90→100%: 収穫逓減。残りの失敗が重要かどうか判断してから追求する

ユーザーはいつでも「止める」「続ける」を判断できる。

**収束後のevalの扱い（卒業と飽和）:**
- 収束したevalは**回帰スイートへ卒業**させる — 以後はほぼ100%パスを維持すべき回帰チェックとして、スキル修正時やモデル更新時に再実行する。回帰evalのフェイルは即対応
- パス率100%に張り付いたevalは改善シグナルを持たない（**飽和**）。能力向上を続けたい場合は、より難しい新しいテストケースを追加する
- capability用（低パス率から改善を導く）とregression用（100%維持を監視する）の役割を混ぜない — 混ぜると両方の機能を失う

### hold-outテストの導入

イテレーション3（または収束基準を初めて満たした時点）で、hold-outシナリオを実行する。hold-outのパス率がチューニングセットより **15ポイント以上** 低ければ過適合の兆候。直近のイテレーションで追加した制約が特定のテストケースに過度に最適化されていないか確認する。

## ブラインド比較（上級）

2つのスキルバージョンのより厳密な比較が必要な場合に使用。独立したエージェントにどちらがどのバージョンか知らせずに品質を判定させる。

**position bias対策**: LLM judgeは提示位置（AかBか）を系統的に好むバイアスを持つ。A/Bの割り当てをランダム化した上で、**提示順を入れ替えた2回の比較**を行い、判定が一致した場合のみ確定とする。不一致ならTIEとして扱うか、3回目で多数決を取る。

詳細は [agents/comparator.md](agents/comparator.md) と [agents/analyzer.md](agents/analyzer.md) を参照。

オプション機能であり、サブエージェントが必要。通常はヒューマンレビューループで十分。

## description自動最適化

スキル改善後にdescriptionのトリガー精度を最適化する。

### Step 1: トリガー評価クエリを生成

20個の評価クエリ（should-trigger / should-not-trigger の混合）を作成。具体的でリアルなクエリにする（ファイルパス、個人コンテキスト、カジュアルな表現を含む）。

should-not-trigger のクエリは**ニアミス**が最も価値がある — キーワードは共有するが実際は別のことが必要なケース。

### Step 2: ユーザーにレビューしてもらう

評価クエリのリストをユーザーに提示し、追加・修正してもらう。

### Step 3: 最適化

各クエリに対してdescriptionがトリガーするかを確認し、トリガー精度が低い場合はdescriptionを調整する。60%/40%でtrain/test分割し、過学習を防ぐ。各descriptionを3回実行して信頼性のあるトリガー率を取得。

### Step 4: 結果を適用

`best_description` をスキルのフロントマターに更新。ユーザーに before/after とスコアを報告。

詳細は [references/description-guide.md](references/description-guide.md) を参照。

## 環境固有の指示

### Claude.ai（サブエージェントなし）
- **Phase 0（静的レビュー）**: サブエージェントもランも不要なのでそのまま実行できる。この環境では最も費用対効果が高いフェーズ
- **テスト実行**: 並列実行不可。スキルのSKILL.mdを読んで自分でタスクを実行する。ベースラインランは省略
- **結果レビュー**: ブラウザが使えない場合はビューアーを省略し、会話内で結果を直接提示
- **ベンチマーク**: 定量ベンチマークは省略。定性フィードバックに集中
- **description最適化**: `claude -p` が必要なため省略
- **ブラインド比較**: `agents/comparator.md` は使用不可

### Cowork
- サブエージェントが使えるので主要ワークフローは全て動作する
- ブラウザ/ディスプレイがないため結果はファイルに出力してユーザーに共有する
- フィードバックは `feedback.json` として保存される
- description最適化はCoworkで問題なく動作するが、スキルが完成してユーザーが承認するまで待つ
